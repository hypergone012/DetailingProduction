# Новая студия за 6 минут

Новая студия — это **папка с конфигом и фото**, а не новый код, сборка или проект Supabase. Код, фронтенд и функции общие для всех студий; студия появляется в БД после `tenant:publish` и сразу открывается по адресу `APP_URL/s/<slug>/`.

Нужно заранее:

- репозиторий, `pnpm install`;
- доступ к целевой среде:
  - **локально:** запущенный стек (`pnpm stack start`; ключи берутся из `.local/` сами);
  - **hosted:** переменные `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `APP_URL` и, для демо-владельца, `TENANT_DEMO_OWNER_PASSWORD` (SETUP.md §3).

Время по шагам ниже — ориентир для человека, у которого уже есть контакты, часы, список услуг и фото. Сами команды на локальном стеке идут секунды (замер — в конце).

---

### 0:00 — создать папку студии

```bash
pnpm tenant:new detail-pro --name "Detail Pro" --timezone Asia/Yekaterinburg
```

Команда копирует `tenants/_template` в `tenants/detail-pro/` и делает три вещи:

- выдаёт новый `id` (uuid);
- ставит статус `draft`, то есть студия не публична;
- печатает следующие шаги.

`slug` пишется латиницей в нижнем регистре, допустимы цифры и дефис, длина до 40 символов. Зарезервированные `owner`, `api`, `admin`, … схема не пропустит.

### 0:30 — заполнить `tenants/detail-pro/business.json`

Редактор подсказывает поля по `$schema` (`tenants/business.schema.json`). Минимум для первой публикации:

| Поле | Что указать |
|---|---|
| `status` | `"demo"` — студия видна, записи помечены демо, **уведомления не отправляются никому**. `"live"` — только когда выполнены проверки готовности (ниже). |
| `profile` | `tagline`, `description`, `address`, `phone` (E.164), по желанию `email`, `website`, `mapUrl`, `socials`. |
| `branding.themePreset` | одна из 7 тем: `white`, `black`, `red`, `blue`, `green`, `yellow`, `purple`. |
| `branding.accent` | фирменный цвет `#rrggbb` или `null`. Слишком «кислотный» или неконтрастный цвет схема отклонит и объяснит почему. |
| `timezone` | IANA-зона студии. Расписание, слоты и тексты уведомлений считаются в ней. |
| `hours` | `mon`…`sun`: до 4 интервалов `["09:00","20:00"]` в день. Ночной интервал (`["22:00","02:00"]`) допустим. Дня нет в списке — выходной. |
| `exceptions` | праздники и короткие дни. |
| `resources` | боксы и посты: `key`, `type` (например `detail_bay`, `wash_bay`), `name`. |
| `services` | `key`, `name`, `category`, `durationMin`, `price` (в рублях; в БД хранятся копейки), `resourceTypes`. По желанию: `variants` по типу кузова, `addons`, `bufferBeforeMin` / `bufferAfterMin`, `multiDay`, `requiresConfirmation`, `images`. |
| `policy` | шаг слотов, минимальное время до записи, горизонт, срок отмены, лимит активных записей на телефон. |
| `ai` | дневной лимит запросов и токенов помощника для этой студии. |
| `owners` | `[{ "email": "…", "role": "owner" }]`. Сотрудников добавляют с ролями `manager` / `staff`. |

Ошибки схемы приходят с путём поля и понятным текстом. Например:

- `services.2.resourceTypes — нет ресурса типа "wash_bay"`;
- пересекающиеся часы;
- дубли ключей.

### 2:30 — фото и логотип (`tenants/detail-pro/assets/`)

| Файл | Требование |
|---|---|
| `logo.svg` (или PNG) | PNG — от 256 px. SVG в хранилище не попадает: он растеризуется в PNG. |
| `icon.png` | квадрат от 512 px. Из него делаются иконки PWA: any, maskable, apple, favicon. |
| `hero.jpg` | ширина от 1200 px. |
| `gallery/*`, `services/*` | ширина от 800 px и от 600 px. Пути указываются в `branding.gallery` и `services[].images`. |

Шаблон содержит сгенерированные иллюстрации (`branding.demoArtwork: true`). С ними студию можно опубликовать как `demo`, но не как `live`. Заменили на реальные фото — поставьте `"demoArtwork": false`. Все изображения публикация сама превращает в адаптивные WebP и загружает в Storage по хешу содержимого: повторная публикация ничего не перезаливает.

### 4:00 — проверить

```bash
pnpm tenant:validate detail-pro
```

Проверяются:

- Zod-схема;
- размеры и форматы фото;
- перекрёстные ссылки (услуга → тип ресурса, доп. услуги, рекомендации);
- уникальность `id` и `slug` среди всех студий репозитория.

### 4:30 — опубликовать

```bash
pnpm tenant:publish detail-pro            # --dry-run покажет план без записи
```

Публикация:

- загружает медиа;
- создаёт владельцев в Supabase Auth;
- в одной SQL-транзакции (`api_admin_publish_tenant`) создаёт или обновляет студию, услуги, ресурсы, часы и права.

Как владелец получает доступ:

- **demo:** в локальном стеке печатается пароль `demo-owner-2026`; в hosted-среде действует `TENANT_DEMO_OWNER_PASSWORD`;
- **draft / live:** для нового владельца печатается **одноразовая ссылка установки пароля**. Её нужно передать владельцу.

Повторный запуск того же конфига печатает `no changes (idempotent republish)`. Правка конфига и повторная публикация меняют только изменённое. Записи, клиенты, оплаты и правки, сделанные владельцем в кабинете, не трогаются (`--overwrite` — сознательно перезаписать правки кабинета).

### 5:00 — проверить живую студию

```bash
pnpm tenant:verify detail-pro                                  # API, медиа, манифесты, слоты, владелец
pnpm tenant:verify detail-pro --app-url=https://app.example.com  # + страницы и статические оболочки
```

`tenant:verify` проверяет студию настоящими HTTP-запросами:

- bootstrap студии не содержит приватных полей;
- медиа доступны и принадлежат этой студии;
- манифесты client и owner корректны (`id`, `scope`, иконки 192/512/maskable);
- есть свободные слоты;
- есть владелец;
- демо-студия ничего не отправляла;
- с другими студиями нет общих услуг и медиа.

### 5:30 — оболочка для установки PWA (только hosted)

```bash
SUPABASE_URL=… SUPABASE_SERVICE_ROLE_KEY=… APP_URL=… pnpm tenant:shells   # в уже собранный apps/web/dist
```

Фронтенд **не пересобирается**. `tenant:shells` дописывает в `dist` для каждой опубликованной студии:

- `index.html` с её названием, цветом темы, иконками и OG;
- манифесты client и owner;
- правила `_redirects`.

После этого `dist` нужно выложить заново. Без этого шага студия тоже работает: приложение возьмёт название и манифест из API. Шаг нужен для превью ссылок и для правильной иконки при установке до первого запуска.

### 6:00 — отдать владельцу

- клиентам: `APP_URL/s/detail-pro/`;
- владельцу: `APP_URL/s/detail-pro/owner/` (email из `owners` и пароль либо ссылка из шага публикации).

## Перевод в live

Владелец нажимает **Студия → Режим работы** в кабинете. Кабинет показывает чек-лист, и SQL перепроверяет его в момент перехода:

- указаны телефон и адрес;
- задано рабочее время;
- есть активный ресурс;
- есть услуга для онлайн-записи, которую может выполнить ресурс студии;
- демо-иллюстрации заменены реальными фото;
- есть владелец.

Другой путь — `"status": "live"` в `business.json` и `pnpm tenant:publish`. Те же проверки делают схема и SQL.

Записи, созданные в демо-режиме, остаются помеченными (`is_demo`) и никогда не порождают уведомлений.

## Чего делать не нужно

- писать код или ветвиться по slug: `security:scan-bundle` ищет названия и slug всех студий из `tenants/` в общем коде и в сборке, а eslint запрещает сравнения со slug демо-студий;
- пересобирать фронтенд или функции;
- создавать новый проект Supabase, новые бакеты или новые ключи.

## Удалить студию

```sql
delete from public.tenants where id = '<uuid>';   -- все строки студии удаляются каскадом
```

Медиа под префиксом `<tenant_id>/` удаляются через Storage API (SETUP.md §5). После этого удалите папку `tenants/<slug>` и выполните `pnpm tenant:shells`.

## Замер

Проверено 2026-10-02 на локальном стеке: скретч-студия из шаблона прошла весь путь, после чего была удалена.

| Шаг | Результат | Время |
|---|---|---|
| `tenant:new` | папка, новый id, статус draft | 1,3 с |
| правка `business.json` | `status: demo`, владелец, телефон, адрес | — (вручную) |
| `tenant:validate` | ✓, 3 предупреждения: пустые SEO-поля, демо-иллюстрации | 1,5 с |
| `tenant:publish` | студия, ресурс, услуга, 5 медиа (16 файлов), владелец, пароль демо-владельца | 2,0 с |
| `tenant:publish` повторно | `no changes (idempotent republish)`, 0 загрузок | 1,8 с |
| `tenant:verify --app-url` | 10 passed, 1 warning: нет статической оболочки, т. к. `tenant:shells` ещё не запускался | 1,2 с |
| `build` + `tenant:shells` | оболочки и манифесты 3 студий, `_redirects` | 11,1 с + 1,0 с |
| `tenant:verify --app-url` | **11 passed, 0 failed, 0 warnings** | ~1 с |
| вход в кабинет (Chromium, Pixel 7) | клиентская страница с названием студии, вход владельца → «Сегодня», манифест `/s/<slug>/owner/manifest.webmanifest`, без ошибок консоли | — |

Пересборка фронтенда в шаге `build` понадобилась только потому, что в этой среде был старый `dist`. Для новой студии она не нужна.

Время работы с данными студии (тексты, цены, фото) зависит от того, насколько они готовы. «6 минут» — это путь с готовыми данными. Сами команды занимают меньше 10 секунд.
