# Сайт на своём сервере в России: открывается без VPN

## Зачем переезжать

Сейчас сайт работает на `*.pages.dev` (Cloudflare Pages), а база и вход — на `*.supabase.co`. Октябрь 2026, проверка из России зондами Globalping (workflow **Diagnose network**):

- **`pages.dev`.** TLS-соединение рвётся или не устанавливается: страница не открывается.
- **`supabase.co`.** Соединение не устанавливается по таймауту: услуги и запись не работают, даже если страница открылась.

Свой домен, подключённый к тем же Cloudflare и Supabase, не помогает: трафик идёт тем же маршрутом.

**Решение.** Вся платформа переезжает на один ваш сервер в России, под одним адресом, например `https://app.studio.ru`:

- сайт;
- база записей и клиентов;
- вход владельца;
- фото;
- уведомления.

Зарубежные CDN и сервисы во время работы не нужны. Персональные данные клиентов хранятся в РФ (152-ФЗ).

## Что понадобится

| Что | Где взять | Примерная цена |
|---|---|---|
| **VPS:** Ubuntu 24.04, x86_64, 2 vCPU, 4 ГБ RAM, от 40 ГБ диска, публичный IPv4 | любой российский хостинг: Timeweb Cloud, Selectel, REG.RU, Yandex Cloud, VK Cloud, Beget | 600–1500 ₽/мес |
| **Домен** (например `studio.ru`) | REG.RU, Timeweb, RU-CENTER | 200–900 ₽/год |

На всё уйдёт около 20 минут вашей работы. Остальное делает кнопка в GitHub.

## Шаг 1. Сервер

1. Закажите VPS с образом **Ubuntu 24.04**. Регион — Россия (Москва или Санкт-Петербург).
2. Запишите **IP-адрес** и **пароль root** из письма или панели хостинга. Если умеете, добавьте SSH-ключ: это надёжнее пароля.
3. Больше на сервере ничего делать не нужно: остальное установит кнопка.

## Шаг 2. Домен

1. Купите домен.
2. В панели DNS домена создайте **A-запись**:
   - **имя:** `app` (адрес будет `app.studio.ru`) или `@` (сам `studio.ru`);
   - **значение:** IP сервера.
3. Подождите, пока запись заработает: обычно 5–30 минут. Проверка: на компьютере выполните `nslookup app.studio.ru`, должен вернуться IP сервера.

AAAA-запись (IPv6) не создавайте, если не уверены, что у сервера настроен IPv6.

## Шаг 3. Секреты в GitHub

Откройте репозиторий → **Settings → Secrets and variables → Actions → New repository secret**.

| Секрет | Что вставить | Нужен? |
|---|---|---|
| `SERVER_HOST` | IP сервера | да |
| `SERVER_PASSWORD` | пароль root | да, если нет ключа |
| `SERVER_SSH_KEY` | закрытый SSH-ключ целиком, от `-----BEGIN` до `END-----` | вместо пароля |
| `SERVER_USER` | пользователь, если не `root` (ему нужен `sudo` без пароля) | нет |
| `SERVER_PORT` | порт SSH, если не 22 | нет |
| `SERVER_HOST_KEY` | строка ключа сервера, чтобы GitHub узнавал именно ваш сервер; её печатает первый запуск («ключ сервера: …») | рекомендуется |
| `ACME_EMAIL` | ваша почта для писем Let's Encrypt о сертификате | нет |
| `DEMO_OWNER_PASSWORD` | уже есть: пароль демо-кабинета | да |
| `LLM_API_KEY` | уже может быть: ключ умного помощника | нет |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_SENDER` | почта для «Забыли пароль?» (как в DEPLOY-IN-BROWSER.md, 7.3; например `smtp.yandex.ru`, `465`) | для настоящих владельцев |

Секреты Supabase (`SUPABASE_*`) и Cloudflare (`CLOUDFLARE_*`) не удаляйте: они нужны для переноса данных (шаг 4) и переадресации старого адреса (шаг 6).

## Шаг 4. Запуск

1. **Actions → Deploy server (Russia) → Run workflow.**
2. Заполните поля:
   - **Домен** — например `app.studio.ru`, без `https://`.
   - **Перенести из Supabase** — отметьте **только при первом запуске**, если в старом сайте уже есть настоящие записи, клиенты, фото или владельцы. Перенос идёт только на пустой сервер: если там уже есть данные, кнопка остановится и ничего не затрёт.
   - **Проверить из России** — оставьте включённым.
3. Нажмите **Run workflow** и подождите 10–15 минут при первом запуске; повторные запуски быстрее.

Что делает кнопка:

1. **Сервер.** Ставит PostgreSQL и сервисы платформы и получает HTTPS-сертификат.
2. **Секреты.** Создаёт их на самом сервере; они не покидают сервер и не печатаются в журнал.
3. **База и студии.** Применяет миграции и публикует студии.
4. **Сайт.** Собирает сайт под ваш домен и выкладывает его без простоя.
5. **Проверка.** Открывает каждую страницу и API через публичный адрес.
6. **Проверка из России.** Зонды Globalping в РФ скачивают страницу, скрипты, стили, данные студии и фото.

При переносе из Supabase переезжают:

- записи, клиенты, автомобили, оплаты, история;
- аккаунты владельцев (пароли прежние);
- все фото;
- ключи ссылок на записи и push-уведомлений, поэтому старые ссылки клиентов продолжают работать.

## Шаг 5. Результат

- **Зелёная галочка** у шага «Выкладка на сервер»: сайт установлен и проверен.
- **Шаг «Проверка из России»** в Summary показывает итог:
  - **PASS** — каждая часть сайта загрузилась у российских зондов;
  - **FAIL** — что-то не грузится (таблица покажет, что именно и у какого оператора);
  - **NOT CONFIRMED** — зонды не ответили (лимит сервиса). Запустите **Diagnose network** с адресом `https://ваш-домен/s/graphite/` позже.
- **Проверьте сами.** Телефон, **Wi-Fi и VPN выключены**, мобильный интернет: откройте `https://ваш-домен/s/graphite/` и запишитесь. По возможности проверьте у двух-трёх операторов (МТС, Билайн, МегаФон, Tele2). Автоматическая проверка зондами не заменяет проверку с реальной SIM-карты.

Кабинет владельца: `https://ваш-домен/s/graphite/owner/`.

## Шаг 6. Старый адрес → новый

После переезда старый сайт `*.pages.dev` всё ещё работает за границей и через VPN, и записи через него ушли бы в старую базу. Закройте его:

1. **Actions → Redirect old site → Run workflow.**
2. **Новый адрес** — `https://ваш-домен`; **имя проекта** — как в старом Deploy (`detailing-studio`).

После этого любая старая ссылка, включая ссылки клиентов на их записи, открывает ту же страницу на новом адресе. Установленное старое приложение само удаляет свой кэш и переходит на новый адрес. Установить приложение на телефон заново нужно уже с нового адреса: приложение привязано к адресу сайта.

Когда убедитесь, что всё работает, проект Supabase можно поставить на паузу.

## Обновления

Любые изменения выкладываются той же кнопкой **Deploy server (Russia)**, уже без «Перенести из Supabase». Запуск можно повторять сколько угодно:

- записи, клиенты, фото и секреты сохраняются;
- сайт переключается на новую версию мгновенно;
- открытые у клиентов страницы не ломаются.

## Резервные копии

- **Когда.** Каждую ночь сервер сохраняет базу, фото и секреты в `/var/backups/dp`.
- **Сколько хранятся.** Копии хранятся 7 дней.
- **Что сделать вам.** Раз в неделю скачивайте их к себе.

Как скачать и восстановить: [deploy/server/RESTORE.md](deploy/server/RESTORE.md).

## Безопасность сервера

- **Порты.** Наружу открыты только 80/443 (сайт) и 22 (SSH). База и все сервисы слушают только `127.0.0.1`.
- **Секреты.** Хранятся в `/etc/dp` (права 600, только root), генерируются на сервере и в GitHub не попадают.
- **SSH.** После первого запуска лучше перейти на вход по SSH-ключу (`SERVER_SSH_KEY`) и отключить вход по паролю в панели хостинга.

## Что работает иначе, чем на Supabase

- **Умный помощник с LLM.** API Anthropic не обслуживает запросы из России. С российского сервера помощник отвечает по шаблонам: цены, свободное время, адрес. Запись при этом работает полностью.
- **«Забыли пароль?»** Нужны секреты `SMTP_*`; без них письма не уходят. Демо-владельцы входят с `DEMO_OWNER_PASSWORD`.
- **Push-уведомления.** Сервер отправляет их через службы браузеров (Google, Apple, Mozilla). Доставку с российского сервера на конкретные телефоны мы не проверяли — проверьте на своём устройстве.
